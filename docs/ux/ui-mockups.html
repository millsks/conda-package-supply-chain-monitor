D1

How a fact becomes a screen

Pipes and filters over an append-only log. Collectors share nothing but the log; policy is a separate versioned pass; the application reads derived state and never computes it. Every screen in this document sits at the right-hand end of this picture.

D1Collection → evidence → policy → surface Dependency direction is one-way. Nothing on the right writes to the left.
Two writes, both human

Queue actions write workflow state. The package-identity override writes governed reference data. Nothing else in the application writes anything.

Cut-off, not "now"

A policy run reads the log at a stated cut-off, so re-running the same version against the same cut-off reproduces the same screen.

Failure is a value

A rate-limited source degrades to stale evidence and a visible error run, never to a clean result.

The rollup is the read model

Every screen from 3 onward reads one rollup row per package plus the evidence rows behind it. None of them recomputes a status.

D2

Screen map and role gates

One sign-in, one claim resolution, three role lanes. Reading evidence is shared by all three roles; queues are role-exclusive, and reaching for another role's queue produces a logged refusal rather than an empty page.

D2Navigation, with what each role may reach Numbers key to the screens below.

The five outcome states, drawn apart

The product's primary failure mode is an unknown rendered as clean. So the four sentinels are given their own colour and their own marker shape — a hollow ring, a dashed ring, a struck circle, a triangle — and none of them is ever a blank cell. Status values are emitted lowercase and verbatim on every surface, screen and export alike.

current

Determinate. Policy reached a conclusion from evidence inside its freshness target. Green, amber and red are all determinate — a filled dot.

unknown

Nobody has established this. No evidence, or evidence the collector could not match. Hollow ring. Never displayed as clean, never omitted from a count.

not_found

Looked, and it is not there. The lookup succeeded and returned nothing — no PyPI project, no feedstock. Dashed ring. Distinct from unknown.

not_applicable

The check does not apply. A native library has no Requires-Python. Struck circle. Modelled from v1 so the non-Python phase exercises a path that exists.

error

The collection itself failed. Rate limit, timeout, bad response. Triangle. Carries a trace identifier, so it is investigable rather than merely recorded.

stale

Past its freshness target. An overlay on any determinate value: the conclusion is shown, struck through with an amber evidence line, and cannot be acted on.

What the confidence gate does to a row

  • verified — comparisons and recommendations render normally.
  • inventory-derived — the same values render, tagged lower confidence; the tag is on the row, not a footnote at the bottom of the page.
  • unmapped — every gated status is written as unknown. The row still appears in the health view and still holds a rollup row; it simply never claims the package is current, clean, or lacking a feedstock, and it is routed to the identity review queue instead.

Facets swap the table, not the page

hx-get="/packages/" with hx-target="#health-rows", hx-push-url="true" and hx-indicator. The URL stays shareable and the back button works, because every filter is a query parameter Django already parses.

CPM-FR-23

Alpine holds only view state

x-data tracks which facet groups are open and the pending filter set before it is submitted. No status, count or timestamp is ever computed client-side.

CPM-AD-10

Pagination cannot be opted out of

Page size and its ceiling are set globally in REST_FRAMEWORK, and the HTML view reads the same constants. No filter combination returns the unbounded inventory.

CPM-NFR-4CPM-AD-12

Read the unmapped row

internal-telemetry-sdk is present, ranked, and carries a rollup row — with every gated status written as unknown. It is never absent from a count and never reported as having no feedstock.

CPM-FR-5CPM-AD-4

Sort is bucket then score

Rank is derived and stable for a policy run, so two people sorting the same view at the same cut-off see the same order.

CPM-FR-20

Query count is bounded by a test

The p95 budget is still an open question, but the story requires one to exist and to be enforced — a regression fails the suite rather than merely running slower.

D4

What a queue item can do

One table serves all three queues. An item is keyed on a finding key that survives re-observation, transitions are declared as data with the role each one requires, and routing between queues changes a field rather than creating a second item.

D4Workflow item states and the role each transition requires State names are illustrative — the spine fixes the mechanism, not the vocabulary.
D5

What stays in the request, and what leaves it

The rule that keeps the application responsive: a view reads derived state and may write workflow state or an override. Anything that makes an outbound call, runs a collector or a policy pass, or exports beyond the row cap becomes a job — and the interface says so rather than waiting.

D5The request/task boundary, as the user experiences it HTMX swaps on the left; Celery queues on the right.
§

What is specified, and what this mockup invented

A mockup has to be concrete, and the planning artefacts deliberately leave some things open. Everything invented here is listed so that nobody downstream mistakes a drawing for a decision.

Taken directly from the brief, PRD and spine

  • The three roles, what each reads and what each acts on.
  • The five outcome states, their lowercase values, and the rule that no surface collapses them.
  • Confidence values and the gate they apply, distinct from match confidence.
  • The rollup: one row per package always, carrying computed_at, the cut-off, and a per-domain version map.
  • Evidence tables and their columns; the run ledgers as a separate class.
  • One workflow table, three filtered queues, items keyed on a finding key, transitions as (from_state, to_state, required_role) data.
  • The override as the only human write to governed reference data, with a required reason and an audit row in the same transaction.
  • The six recurring reports, each stating its cut-off and policy version.
  • Structural pagination, the request/task boundary, and the three Celery queues.
  • The export column contract — historical headings over snake_case stored fields.
  • The natural-language capability as post-MVP and read-only over governed views.

Invented for this mockup — not decisions

  • URL paths (/packages/, /queues/compliance/). No route table is specified anywhere.
  • Workflow state names — open, triaged, routed, in_progress, resolved, accepted. The spine fixes the mechanism; the vocabulary is open.
  • Priority rule names (kev_with_fix, no_feedstock_high_usage) and every bucket assignment shown. The rule set and score function are Open Question 8 and block CPM-EP-PRIORITY.
  • Freshness targets — 24h, 7d, 30d. Open Question 7.
  • The 500-row synchronous export cap and any latency figure. Open Question 5.
  • Advisory source names and licence policy outcomes. Open Questions 1 and 2.
  • Channel names (conda-forge/noarch, internal/linux-64). Open Question 4.
  • The 14-month feedstock inactivity threshold. Open Question 10.
  • The internal usage field values — components, lines of business, downloads. The field set is settled (Open Question 3, resolved 2026-09-04): internal_component_count and internal_lob_count are required on every inventory record, while downloads may be blank. The values shown here are still invented, and a blank signal means missing — never zero.
  • All package names, CVE identifiers, versions, counts and timestamps.

Notes for whoever builds this

  • Bootstrap 5.2 is already in the base template. The mockups above are drawn in a neutral system, but every component shown maps onto what the platform already loads — table, badge, form control, modal, offcanvas for the facet panel on narrow screens.
  • HTMX earns its place on four interactions: facet swaps on the health view, evidence disclosure on package detail, queue transitions posting a form and swapping a row, and job polling. Everything else can be a plain page load.
  • Alpine holds view state only — open panels, pending filter selections, bulk checkboxes, modal focus. It never computes a status, a count, or a timestamp, because derived state is read-only to the application.
  • Every partial is a template fragment the full page also renders, so a swapped table row and a freshly loaded page cannot disagree.
  • The freshness bar is a single inclusion tag used by screens 2, 3, 4, 6, 8 and 9 and by the export header — one implementation, so a surface cannot forget it.
