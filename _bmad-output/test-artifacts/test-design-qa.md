# Test Design for QA: Conda Package Supply Chain Monitor (System-Level)

**Purpose:** Test execution recipe for the QA/test engineers who will write these tests. Defines what to test, how to test it, and what QA needs from other teams.

**Date:** 2026-09-03
**Author:** Murat (BMad TEA — Master Test Architect)
**Status:** Draft
**Project:** conda-package-supply-chain-monitor

**Related:** See the architecture companion (`test-design-architecture.md`) for the full testability review (TC-1 … TC-7), the ASR dispositions, and the unabridged risk register.

---

## Executive Summary

**Scope:** System-level test design across all 9 epics / 42 stories / 131 acceptance criteria, covering 41 `CPM-FR-*`, 13 `CPM-NFR-*` and 24 `CPM-AD-*`. No implementation exists yet, so this plan is written to be built alongside the code rather than retrofitted to it.

**Risk Summary:**

- Total Risks: 14 (11 high-priority score ≥6, 3 medium/low)
- Critical Categories: DATA (5 risks, including all three score-9s), OPS (3), SEC (2), BUS (2), TECH (2), PERF (1)
- R-01, R-02 and R-03 all score **9** and are three routes to the same outcome — a package reading clean when it is unassessed, contradicted, or stale — which `CPM-SM-C1` names as the product's defining failure.

**Coverage Summary:**

- P0 tests: ~31 (the three nines, the AUDIT harness, append-only guarantees, analytics permissions)
- P1 tests: ~22 (journeys, routing audits, concurrency, pagination and export audits)
- P2 tests: ~2 (adoption and cadence audits)
- P3 tests: exploratory only — advisory-source behaviour, unblocked once PRD OQ 1 resolves
- **Total**: ~55 scenarios (~80–130 hours, spread across the epics rather than front-loaded)

## Dependencies & Test Blockers

**CRITICAL:** QA cannot proceed without these items from other teams.

### Backend/Architecture Dependencies (Pre-Implementation)

**Source:** See the architecture companion's testability review for the detailed mitigation plans. All five are marked **ACTIONABLE** and all five are cheap now and expensive after `CPM-EP-EVIDENCE` ships.

1. **ASR-1 — An injectable clock, used everywhere, enforced by an audit** — Backend / Architecture — before `CPM-EP-EVIDENCE`
   - QA needs a single injectable clock in `core`, used by every collector, policy pass and freshness computation, so a test can advance time.
   - Blocks: freshness, observation windows, policy cut-offs, staleness, KEV catalog dates and `observed_at` all depend on "now" (TC-1). Tests against the real clock are either impossible (you cannot make evidence six months old) or flaky (they pass until they run at midnight). `EVIDENCE.06-UNIT-002` and `EVIDENCE.01-AUDIT-002` cannot be written without it.

2. **ASR-2 — A transport seam in the collector base** — Backend — with `CPM-EVIDENCE-S05`
   - QA needs each collector to be a pure translation from a recorded payload to evidence rows, with the transport seam in the collector base.
   - Blocks: eight collectors read from source repositories, PyPI, conda-forge, advisory sources and the KEV catalog; `tests/unit/` forbids network (TC-2). Without the seam, `parse`, `not_found`, `error` and `not_applicable` handling is testable only in the slow tier, pushing the majority of the product's behaviour into `tests/integration/`.

3. **ASR-3 — A policy-pass registry that makes the single-writer rule auditable** — Backend / Architecture — before the second policy pass exists
   - QA needs passes to register with the policy run rather than being called directly, each declaring the derived table it owns, so the set is enumerable.
   - Blocks: `CPM-AD-21` ("no pass writes the rollup") is a negative property. A test asserting the two current passes do not write the rollup passes today and says nothing about the ninth pass someone adds next quarter (TC-3). `EVIDENCE.07-AUDIT-002` is unwritable without the registry.

4. **ASR-4 — Freshness targets as required configuration, refused at startup when absent** — Backend / Architecture — before `CPM-EP-EVIDENCE` ships
   - QA needs a startup refusal (`ImproperlyConfigured`, per the inherited `CG-3` convention that a refusal raises rather than warns) when a registered collector declares no freshness target.
   - Blocks: `CPM-FR-38` reads a per-collector target that PRD OQ 7 leaves unset. An unset target does not mean "fresh forever" — it means undefined (TC-7). This is the largest false-clean path, and `EVIDENCE.06-AUDIT-001` is the test that closes it.

5. **ASR-5 — `analytics` alias test configuration and the inherited assertion's meaning** — Architecture + platform owners — before `CPM-EP-NL`
   - QA needs a decision: is the inherited `tests/unit/test_database_selection.py` assertion amended to mean "every alias Django may write through", and does the `analytics` alias get a `TEST` mirror?
   - Blocks: `CPM-AD-16` adds an `analytics` alias with `ATOMIC_REQUESTS = False`, colliding with an inherited assertion that deliberately iterates *every* alias because the platform "forecasts a second database" (TC-6). This is a cross-boundary change to inherited code; QA must not amend it unilaterally. `NL.01-UNIT-001` encodes whichever answer is agreed.

**Two ASRs need no action from QA:** ASR-6 (replay determinism as a property test) is already designed and covered by `CPM-PRIORITY-S03`; ASR-7 (correlation ids persisted on run-ledger rows) is already designed and covered by `CPM-EVIDENCE-S03`.

### QA Infrastructure Setup (Pre-Implementation)

1. **The reusable `AUDIT` harness** — QA + Dev, built once in `CPM-EP-EVIDENCE`
   - Roughly a third of the P0 effort is this harness rather than the individual audits. Once it exists, every later `AUDIT` entry in this plan is a few lines.
   - It is a **declared-list plus reconciliation-test** pattern, and it is not new: the platform already runs one. `tests/unit/startup/forbidden_states.py` declares the platform's refusal conditions, `@pytest.mark.forbidden_state("<id>")` tags the test that proves each one, and `tests/unit/startup/test_refusal_coverage_audit.py` mechanically reconciles the two and fails when a declared state has no test.
   - Extend that machinery — do not replace it. Each new invariant gets a declared list (forbidden outcomes, registered passes, evidence models, list endpoints, export paths, task routes) and a reconciliation test that fails when the declaration and the code diverge.
   - `AUDIT` tests read declarations, not data, so they live in `tests/unit/` and cost effectively nothing at gate time.

2. **Test data setup** — QA
   - Append-only evidence makes fixtures trivial: no update ordering and no mutation sequencing, so a test builds history by inserting rows.
   - Collector fixtures are recorded payloads fed through the ASR-2 transport seam; the seam is what makes them unit-tier.
   - Time-dependent fixtures set the ASR-1 injectable clock explicitly. No test reads the real clock.

3. **Test environments** — QA
   - Local: `pixi install`, then `pixi run ci` — the same command that runs in CI. `pixi` is the only Python runner in this project.
   - CI: `pixi run ci` = precommit → build → typecheck → lint → test-cov. The gate is real: 1,545 tests at 97.04% against a 90% floor.
   - Nightly / Weekly: non-gating jobs (volume run, live-transport checks, Python 3.14 build-and-import verification). See Execution Strategy.
   - Tiers: `tests/unit/` (no database, network or filesystem), `tests/integration/` (the `integration` marker is applied automatically by a directory-scoped `pytest_collection_modifyitems` hook, not by decorating each module), `tests/spikes/` (excluded from the gate by filename — `spike_*.py` does not match `python_files` — never by `-m`, and a test enforces that). Registered markers: `integration`, `spike`, `forbidden_state`.

**Example `AUDIT` pattern** — a declared list plus the reconciliation test that keeps it honest:

```python
# django_apps/evidence/policy/registry.py — the declared list
REGISTERED_PASSES: dict[str, str] = {
    "advisory": "advisory_finding",
    "currency": "currency_state",
}
ROLLUP_TABLE = "package_rollup"


# tests/unit/evidence/test_policy_writer_audit.py — the reconciliation test
def test_no_registered_pass_declares_the_rollup() -> None:
    """CPM-AD-21: no policy pass writes the rollup (R-02, TC-3, ASR-3)."""
    offenders = [name for name, table in REGISTERED_PASSES.items() if table == ROLLUP_TABLE]
    assert offenders == [], f"passes declaring the rollup: {offenders}"
```

Run it the same way as everything else:

```bash
pixi run test        # unit tier, including every AUDIT test
pixi run ci          # the full gate: precommit -> build -> typecheck -> lint -> test-cov
```

**The three nines are one risk.** R-01, R-02 and R-03 are not independent findings — they are three routes to a package reading clean when it is unassessed, contradicted, or stale. They score 9 because each is individually probable (the idiomatic Django call, the export contract's own "blank means missing" rule, and an unset configuration value) and because the failure is *silent*: no exception, no alert, and a dashboard that improves as the product gets worse. The mitigation for all three is the same shape — a declared list of forbidden outcomes plus a mechanical audit that every one has a test proving it cannot happen.

## Test Coverage Plan

**IMPORTANT:** P0/P1/P2/P3 = **priority and risk level** (what to focus on if time-constrained), NOT execution timing. See "Execution Strategy" for when tests run — in this project everything below runs on every PR.

**Test levels in this project.** ID format is `{EPIC}.{STORY}-{LEVEL}-{SEQ}` per `test-levels-framework.md`, with epic and story taken from the `CPM-` keys — e.g. `EVIDENCE.02-UNIT-001`.

| Level | Meaning here | Tier |
| ----- | ------------ | ---- |
| `UNIT` | Pure logic, no database, network or filesystem | `tests/unit/` |
| `INT` | Real models, real database, transactions | `tests/integration/` |
| `API` | Through the HTTP layer with DRF's client, including authorization | `tests/integration/` |
| `AUDIT` | **Project-specific.** Mechanically reconciles a declared list of invariants against the tests or code that prove them | `tests/unit/` |

**`AUDIT` earns its own level.** It does not test behaviour — it tests that a rule cannot be violated by code written later. Every `AUDIT` entry below is the existing `test_refusal_coverage_audit.py` pattern pointed at a new invariant, and each is the answer to a negative property that would otherwise rot (TC-3).

**Duplicate-coverage guard applied.** The five-state rule is proven once at each level for a different reason: `AUDIT` that the field type permits all five, `UNIT` that precedence is correct, `INT`/`API` that the boundary does not collapse them on the way out. That is defence in depth on the product's defining failure, not redundancy. Elsewhere, anything provable by an `AUDIT` or `UNIT` test is not repeated at `INT`.

Scenarios below stay grouped by the risk they mitigate, ordered by residual risk rather than by epic.

### P0 (Critical)

**Criteria:** Blocks core functionality + High risk (≥6) + No workaround + Affects majority of users

## Execution Strategy

**Philosophy:** Run everything in PRs unless there is significant infrastructure overhead. The existing suite is 1,545 tests in roughly 30 seconds, and this design keeps everything gating. `AUDIT` tests are the cheapest in the suite — they read declarations, not data — so there is no cost argument for deferring them. **Everything that protects a score-9 risk runs on every PR.**

**Organized by infrastructure cost:**

### Every PR: `pixi run ci` (< 15 min)

**All functional tests** (from any priority level):

- Every `UNIT`, `AUDIT`, `INT` and `API` test in this plan — all ~55 scenarios, P0 through P2
- `pixi run ci` = precommit → build → typecheck → lint → test-cov, the same command locally and in CI
- `tests/unit/` runs without database, network or filesystem; `tests/integration/` picks up the `integration` marker automatically by directory
- Coverage gate: ≥ 90% (currently 97.04%)

**Why run in PRs:** fast feedback, no expensive infrastructure, and the invariants these tests protect are unfixable in place once data exists.

### Nightly: volume run and live-transport checks (not gating)

**Infrastructure-heavy validation** (from any priority level):

- Volume run at 10,000 packages — `CPM-NFR-1` without manual batching, and the p95 latency measurement for `CPM-NFR-5` once PRD OQ 5 supplies a budget
- Live-transport contract checks against the real external sources: source repositories, PyPI, conda-forge feedstocks and channels, advisory sources, the KEV catalog

**Why defer to nightly:** full-inventory scale does not belong in a suite that must stay fast (TC-4), and live outbound calls are neither hermetic nor permitted in the unit tier. The in-gate substitutes are the property assertions — bounded query counts, chunking, pagination enforcement, streaming export — which is what `APP.02-INT-001` and `CURRENCY.05-UNIT-001` exist to cover.

### Weekly: Python 3.14 build-and-import verification (not gating)

**Special infrastructure tests** (from any priority level):

- Build-and-import verification across a package sample — genuinely compute-backed work, executed on the `verify` queue
- Confirms `PY314.02-AUDIT-001`'s configuration claim against real execution: verification work stays off the `collect` queue

**Why defer to weekly:** builds are long-running and compute-backed, and weekly validation of a slow-moving ecosystem question is sufficient.

**Manual / out-of-band validation** (excluded from automation):

- Operator review of the nightly volume job report
- Threshold sign-off on the five UNKNOWN values once their PRD open questions resolve

## Data Prerequisites

No production data is required, and none should be used — the inventory carries internal
usage fields that `CPM-NFR-9` restricts from leaving the system.

| Prerequisite | Why it is needed | Source |
|---|---|---|
| Recorded external payloads per collector | `tests/unit/` forbids network; collector parse logic must be unit-testable (TC-2) | Captured once per source, stored as fixtures beside the collector's tests |
| A package fixture at each confidence level — `verified`, `inventory-derived`, `unmapped` | The confidence gate is the most-branched logic in the product | `factory_boy`, extending `tests/factories.py` |
| Evidence at controlled ages | Freshness and staleness cannot be tested against a real clock (TC-1) | The injectable clock of ASR-1 — never `sleep`, never backdated rows |
| A completed run and an in-flight run | The cut-off must never select a run still `running` | Run-ledger fixtures |
| Two policy passes writing different domains in one run | The rollup-clobbering test needs a genuine second writer | Test-only passes registered with the policy run |
| A package whose type makes a check inapplicable | `not_applicable` must stay distinguishable from `unknown` end to end | A non-Python package fixture, even though v1 targets the Python subset |
| An advisory with a known fixed range | Remediation readiness needs `ready`, `blocked` and `unknown` cases | Synthetic advisory fixtures — **not** live advisory data, which is unresolved (OQ 1) |

**ASR-1 is a hard prerequisite, not a preference.** Three P0 scenarios — `EVIDENCE.06-UNIT-002`,
and the freshness half of `EVIDENCE.06-UNIT-001` and `SECURITY.06-UNIT-001` — cannot be written
at all without an injectable clock.

## Execution Order Within the PR Tier

`AUDIT` → `UNIT` → `INT` → `API`.

Audits run first because they are the cheapest in the suite — they read declarations, not
data — and because they fail on exactly the class of defect that makes every later result
untrustworthy. A run where `EVIDENCE.02-AUDIT-002` fails has an evidence table something can
mutate, and every downstream assertion about history is then meaningless.

The PR tier is deliberately **not** split into smoke and priority waves. At roughly 30 seconds
for 1,545 tests there is nothing to gain, and the `PR / Nightly / Weekly` model stays simple.

## Appendix A: Running and Selecting Tests

**pixi is the only Python runner in this project.** Never invoke `python`, `pip`, `uv` or `pytest` directly — every command below goes through pixi.

```bash
# The gate: precommit -> build -> typecheck -> lint -> test-cov
pixi run ci

# Unit tier only (no database, network or filesystem) — includes every AUDIT test
pixi run test

# Full suite with the 90% coverage floor
pixi run test-cov
```

**Selective execution.** This project has no priority markers; registered markers are `integration`, `spike` and `forbidden_state`, and the `integration` marker is applied automatically by directory. Select by marker or by name expression through the existing tasks:

```bash
# Integration and API tiers only
pixi run test -m integration

# Every AUDIT test, by naming convention
pixi run test -k "audit"

# The inherited forbidden-state reconciliation
pixi run test -m forbidden_state
```

**Test IDs in this plan map to test names.** `EVIDENCE.02-UNIT-001` lives in `tests/unit/evidence/`, `APP.05-API-002` in `tests/integration/app/`. Put the test ID in the test's docstring alongside the risk it mitigates, so a failure names both:

```python
def test_evidence_save_with_pk_raises() -> None:
    """EVIDENCE.02-UNIT-001 (R-06): save() on an instance with a primary key raises."""
```

Spikes are named `spike_*.py` and live in `tests/spikes/`. They are excluded from the gate by filename, never by `-m`, and a test enforces that — do not change either mechanism to get a spike collected.
